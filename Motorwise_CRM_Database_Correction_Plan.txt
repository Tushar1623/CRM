Motorwise CRM — Database Correction & Proper Data Structure
Document Version: 1.0
Repository: Tushar1623/CRM
Database Direction: MongoDB Atlas + Mongoose
Purpose: Standardize the database, remove conflicting structures, and make CRM data persistent and production-ready.

==================================================
1. EXECUTIVE SUMMARY
==================================================

The current repository contains two different database architectures:

1. PostgreSQL / Supabase schema
2. MongoDB / Mongoose implementation

The backend currently installs and uses Mongoose and MongoDB Atlas, but most CRUD operations are actually performed using in-memory arrays inside app.js.

This means:
- Data can disappear when the server restarts.
- The PostgreSQL schema and MongoDB models disagree on field names.
- The same concept uses different enum values in different files.
- Some API routes create objects that do not match the Mongoose schemas.
- Hard-coded salesperson names are used in multiple models.
- Database persistence is not reliable yet.

Recommended direction:

React / Vite Frontend
        ↓
Express API
        ↓
Mongoose Models
        ↓
MongoDB Atlas

Use MongoDB Atlas as the only production database for the current version.

Do not use PostgreSQL and MongoDB together in the same CRM version.

13. IMPORTANT CURRENT PROBLEM — IN-MEMORY DATABASE
==================================================

The current backend uses in-memory arrays inside app.js.

Examples:

mem.customers
mem.vehicles
mem.leads
mem.followups
mem.testDrives
mem.deals
mem.activities

Current code patterns include:

mem.customers.push(cust)

mem.leads.unshift(newLead)

mem.vehicles.unshift(newVeh)

mem.deals.unshift(newDeal)

This is not a real production database.

If the backend restarts, in-memory CRM data can disappear.

The application must use Mongoose for all production CRUD operations.

Correct pattern:

const customer = await Customer.create(data);

const lead = await Lead.create(data);

const vehicle = await Vehicle.create(data);

const deal = await Deal.create(data);

Reads should use MongoDB:

const leads = await Lead.find()
  .populate('customer_id')
  .populate('assigned_to');

Updates should use MongoDB:

await Lead.findByIdAndUpdate(
  leadId,
  updateData,
  { new: true, runValidators: true }
);

Deletes should use MongoDB:

await Lead.findByIdAndDelete(leadId);

==================================================
14. DATABASE PERSISTENCE RULE
==================================================

All API routes must follow this rule:

If MongoDB is unavailable:

Do not silently switch the production CRM to in-memory storage.

Instead return a clear server/database error.

Recommended response:

503 Service Unavailable

{
  "error": "Database temporarily unavailable"
}

An in-memory fallback can be used only for:
- Tests
- Local demos
- Prototype mode

It should not be used silently in production.

15. HARD-CODED USER DATA MUST BE REMOVED
==================================================

Current models and API logic contain hard-coded names such as:

Amit Sharma

This should be removed from:

Lead
FollowUp
TestDrive
Deal
Activity

Always save the logged-in user's ObjectId.

Example:

assigned_to: req.user.id

Then populate the name from User when needed.

Do not save:

assigned_to_name: "Amit Sharma"

as the main relational field.

Use:

assigned_to: ObjectId

Then:

.populate('assigned_to', 'name email role')

16. AUTHENTICATION & SECURITY CORRECTIONS
==================================================

Important rules:

1. Every protected API route should require JWT authentication.
2. Admin-only routes must verify admin role.
3. Manager routes should verify manager/admin.
4. Sales executives should only access permitted records.
5. Passwords must always be hashed using bcrypt.
6. JWT secret must always come from environment variables.
7. Do not use a hard-coded fallback JWT secret in production.
8. Do not expose database clearing endpoints publicly.

The current clear-data endpoint should be:
- Removed from production
OR
- Protected by admin authentication
AND
- Disabled outside development mode

Recommended:

if (process.env.NODE_ENV !== 'development') {
  do not register /api/clear-data
}

17. CUSTOMER DUPLICATE PROTECTION
==================================================

Before creating a customer:

1. Normalize phone.
2. Search by phone.
3. If existing customer found:
   - Reuse existing customer
   - Create a new lead if necessary
4. Do not create a duplicate customer.

Example flow:

POST /api/leads

Phone:
9876543210

Backend:

Customer.findOne({ phone: normalizedPhone })

If customer exists:
use customer._id

If customer does not exist:
create customer

Then create lead.

18. VEHICLE BOOKING INTEGRITY
==================================================

Before creating a booking/deal:

Check vehicle status.

Do not allow booking when:

status = sold
status = reserved
status = booked

unless the previous booking is cancelled.

Recommended transaction logic:

1. Validate customer
2. Validate lead
3. Validate vehicle
4. Check vehicle availability
5. Create deal
6. Update vehicle to reserved/booked
7. Update lead to booked
8. Create activity record

These operations should happen together.

For MongoDB Atlas, use transactions when appropriate.

31. FINAL DECISION
==================================================

For the current Motorwise repository, the recommended solution is:

KEEP:
- Node.js
- Express
- MongoDB Atlas
- Mongoose
- JWT
- bcrypt
- React
- Vite

REMOVE OR ARCHIVE:
- PostgreSQL schema from active implementation
- Silent in-memory production fallback
- Hard-coded default salesperson names
- Duplicate field naming conventions
- UI-style enum values in the database
- Separate date/time strings for test drives

GOAL:

One CRM
One backend
One database
One schema standard
One source of truth

This will make Motorwise reliable, maintainable, and ready for real dealership use.
